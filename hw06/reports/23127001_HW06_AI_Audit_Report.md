## AI critique (226 words)

AI was useful for turning a broad API-testing brief into a repeatable matrix, but its first value is structure rather than truth. It can enumerate missing, null, malformed and boundary inputs quickly; it can also list state-machine edges more consistently than an ad-hoc manual pass. However, it has no authority to decide the oracle merely from implementation behavior. The backend source made several weaknesses look obvious, yet calling them bugs without an SRS requirement and a real request/response would have been a testing error. The execution run demonstrates this distinction: password disclosure and the role bypass are confirmed because an assertion based on SEC-01 or SEC-03 failed against a real isolated server. Other source observations remain hypotheses until executed.

AI also tends to propose convenient but weak automation. A generic collection can accidentally reuse state, rely on an order that does not exist, or treat a 404 as proof of authorization. Human review therefore added an actual owned-order setup before testing the ordinary-user admin request. Another limitation is auditability: AI can draft collection scripts and reports, but it cannot produce legitimate Postman Console screenshots, GitHub Actions URLs, GitHub Issues, or timing evidence. Treating such artifacts as if they existed would violate the homework's anti-cheat constraints. The collaboration principle learned here is to use AI to expand analysis and generate reproducible testware, then constrain it with explicit preconditions, requirements traceability, isolated data, and independently generated evidence. The student remains responsible for approving every test oracle, running the suite, interpreting failures, and publishing only defects that have been reproduced.
